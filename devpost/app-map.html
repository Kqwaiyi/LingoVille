LingoVille App Map

A take-home guide to where things live in the finished proof of concept: one real action traced through the code, where to start a change, and one practice worth reusing.

What the app is

A 3D town in the browser where every errand is a spoken conversation in the language you're learning. The people in town only act on what they understood, and each conversation ends with a short Recap. A few pieces do the work:

  • The townsrc/world: the 3D scene, walking and the people in it.
  • The game rulessrc/sim: money, Patience, Shifts, needs, rent, as plain functions. Every number is in tuning.ts.
  • The contentsrc/content: each place's conversations, items, and the four Culture Packs.
  • The storesrc/store/gameStore.ts: connects the rules, the voice and the screens, and saves.
  • The voicesrc/voice: the live Gemini session, and a scripted stand-in for mock mode.
  • The gatewayserver/: holds the Gemini key and answers /api/*.

One action: ordering a coffee

Route through the code reference route

Three stops, in the order the action happens. Search for the anchor in each file; line numbers drift, names don't.

  1. You press E. src/ui/InteractionPrompt.tsx, the keydown handler that ends in talk('E'). The store's talk action in src/store/gameStore.ts picks the café's conversation and calls startConversation.
    Why it's built this way

    The screens never change the game themselves: they call store actions, and read the game only through selectors. That keeps every rule in one place to test.

  2. The barista is briefed and connected. src/ai/npcSession.ts, buildNpcSession, writes the barista's instructions from orderDrink in src/content/interactions.ts: speak only the Target Language, read the order back, then call serve_order. src/voice/openVoiceSession.ts asks server/gateway.ts (mintToken) for a one-use token and opens the live session.
    Why it's built this way

    The browser never sees the Gemini key: the gateway mints a short-lived token per conversation, and the model and voice come back with it.

  3. The order is served and paid. When the barista calls serve_order, answerToolCall in src/store/gameStore.ts hands it to applyInteractionOutcome in src/sim/interactionOutcome.ts, which checks the item and that you can afford it, then takes the money. ClosingCardPanel in src/ui/ConversationColumn.tsx shows the result.
    Why it's built this way

    The model decides what it understood; the game decides what that costs. A price the model got wrong can't reach your wallet, because the rules check every completion against the menu.

To change this, start here

To change…Start in
A price, the starting money, Patience, or any other game numbersrc/sim/tuning.ts
What a place sells, its signs or its propssrc/content/culturePacks.ts (one pack per language)
What a conversation is for, and how it endssrc/content/interactions.ts
How NPCs are told to behavesrc/ai/npcSession.ts
Which Gemini model or voice is usedserver/config.ts
A label on screensrc/i18n/en.ts, then the same key in ja.ts, zh.ts and de.ts
Where a building or a person standssrc/world/town.ts

A practice to reuse

Give the AI a stand-in behind the same interface. Every conversation goes through one interface, VoiceSession (src/voice/voiceSession.ts). The gateway's mock mode swaps Gemini for a scripted NPC (src/voice/mockVoiceSession.ts) without the rest of the game knowing.

That's what let each build slice be checked the same way every time, with no key and no cost: walk to the barista, order, and see the closing card. On another project that calls an AI model, put the model behind an interface early and write a scripted stand-in for it. Your checks then test your app, not the model's mood that day.
